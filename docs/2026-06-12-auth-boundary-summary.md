## 이 작업이 왜 필요했나 (배경)

우리 인증 구조는 원래 이렇게 생겼습니다:

```
브라우저 ──Supabase JWT──▶ Next proxy / BFF ──검증된 신원 주입──▶ 오케스트레이터
```

Next proxy와 BFF는 요청마다 Supabase에 토큰을 검증하고, 검증된 사용자 ID를 `X-EasyAds-User-Id` 헤더(또는 `userId` 쿼리)로 오케스트레이터에 넘깁니다. 오케스트레이터는 이 값을 **검증 없이 신뢰**합니다 — 신원 확인은 앞단의 일이라는 역할 분담이고, 이 설계 자체는 문제가 없습니다.

문제는 **오케스트레이터 포트에 직접 닿을 수 있는 사람**입니다. 앞단을 건너뛰고 `curl -H "X-EasyAds-User-Id: 남의아이디"` 로 요청하면, 오케스트레이터는 그게 BFF가 보낸 건지 공격자가 보낸 건지 구분할 방법이 없었습니다. 외부 코드 리뷰에서 "이 엔드포인트에 직접 요청을 보내면 어떻게 됩니까?"라고 지적받은 바로 그 지점입니다.

> 💡 **쉽게 말하면:** 회사 건물 1층 로비(proxy/BFF)에서는 신분증 검사를 철저히 하는데, 뒷문(오케스트레이터 직접 접근)으로 들어오면 "저 김부장인데요"라는 말만 믿고 들여보내 주던 상황입니다. 이제 뒷문에서도 직원 출입카드(내부 시크릿)를 요구합니다.

## 1. 오케스트레이터 미들웨어 — 출입카드 검사기

**커밋:** `5a139c83` · **파일:** `orchestrator/app/api/internal_auth.py` (신규), `app.py`

**무엇을:** 모든 요청에 대해 작동하는 FastAPI 미들웨어를 추가했습니다. 동작 규칙:

| 상황 | 동작 |
|---|---|
| `EASYADS_INTERNAL_API_SECRET` **미설정** (로컬 개발, 테스트) | 전부 통과 — 기존과 완전히 동일 |
| 시크릿 설정 + 올바른 `X-EasyAds-Internal-Secret` 헤더 | 통과 |
| 시크릿 설정 + 헤더 없음/틀림 | `401 invalid_internal_secret` |
| `/health` (Railway 헬스체크) | 항상 통과 |

**왜:** 검사를 항상 강제하면 로컬 개발과 테스트 1300여 개가 전부 시크릿 설정을 요구하게 됩니다. "환경변수 하나로 켜는" opt-in 방식을 선택해서(팀 결정 사항), 운영에만 방어선을 세우고 개발 경험은 그대로 뒀습니다.

**어떻게:** 비교는 `secrets.compare_digest`(상수 시간 비교)로 합니다 — 일반 `==` 비교는 글자가 틀린 위치에 따라 응답 시간이 미세하게 달라져서, 이론상 시크릿을 한 글자씩 알아낼 수 있기 때문입니다(타이밍 공격). 헤더값은 공격자가 제어하므로 바이트로 인코딩해 비교합니다.

> 💡 **쉽게 말하면:** 출입카드 검사기를 달되, 검사기 전원 스위치(환경변수)는 따로 뒀습니다. 운영 건물에서만 켜고, 개발 사무실에서는 꺼둡니다. 카드 대조도 "틀린 즉시 삐-" 가 아니라 항상 같은 시간 걸리는 방식이라, 반응 속도로 카드 번호를 유추할 수 없습니다.

## 2. Next proxy — 출입카드 자동 지참

**커밋:** `74434944` · **파일:** `apps/web/app/api/_proxy/orchestrator.ts`

**무엇을:** proxy가 오케스트레이터로 요청을 보낼 때, 환경변수에 시크릿이 있으면 `X-EasyAds-Internal-Secret` 헤더를 자동으로 붙입니다. 4줄 추가.

**왜:** 오케스트레이터가 검사를 시작하면, 정당한 호출자도 카드를 들고 다녀야 하니까요. 환경변수가 없으면 헤더도 안 붙어서(테스트로 확인) 기존 환경에 영향이 없습니다.

> 💡 **쉽게 말하면:** 1층 로비 직원에게 출입카드를 지급했습니다. 카드 제도가 없는 건물(시크릿 미설정)에서는 카드 없이 그냥 다니던 대로 다닙니다.

## 3. BFF — 같은 카드, 5개 통로 전부

**커밋:** `02faf500` · **파일:** `apps/bff/src/app.js`

**무엇을:** BFF가 오케스트레이터를 호출하는 통로는 정확히 5개의 헬퍼 함수(`proxyJson`, `proxyPatchJson`, `proxyDeleteJson`, `proxyGetJson`, `proxyBinary`)입니다. grep으로 전수 확인한 뒤 5곳 모두에 시크릿 헤더를 붙였습니다.

**왜 (그리고 주의한 것):** BFF에는 오케스트레이터가 아닌 **Supabase로 가는 fetch도 하나** 있습니다(JWT 검증용). 여기에 내부 시크릿이 딸려 나가면 외부 서비스에 우리 시크릿을 흘리는 셈이라, 이 호출은 의도적으로 제외했고 그 제약을 테스트와 계획서에 명시했습니다.

> 💡 **쉽게 말하면:** 사내 통로 5곳에는 전부 카드를 찍고 다니게 했지만, 외부 우체국(Supabase)에 갈 때는 사내 출입카드를 보여주지 않습니다. 보여줄 필요도 없고, 보여주면 카드 정보가 새는 거니까요.

## 4. 계약 문서 — "직접 curl하면 어떻게 되나요?"의 공식 답변

**커밋:** `06954f79` · **파일:** `docs/auth-boundary.md` (신규), `.env.example`

**무엇을:** 누가 무엇을 검증하는지를 표로 박은 문서를 만들었습니다. 핵심 내용:

- 오케스트레이터가 신원 헤더를 신뢰하는 건 **버그가 아니라 설계**이고, 그 신뢰가 안전하려면 (1) 네트워크에서 직접 노출 금지, (2) 내부 시크릿 — 두 겹이 필요하다는 것
- "오케스트레이터에 직접 curl하면?" → 운영(시크릿 설정): 어떤 신원 헤더를 위조하든 401 / 로컬(미설정): 기존과 동일
- 시크릿 생성법(`openssl rand -hex 32`), 세 서비스 설정 위치, 로테이션 절차

**왜:** 코드만 있으면 6개월 뒤 "이 헤더 검증 왜 없어요?"라는 질문이 다시 나옵니다. 면접/리뷰에서 받은 질문에 대한 답을 문서로 못 박는 게 이 과제의 절반이었습니다.

> 💡 **쉽게 말하면:** 건물 보안 규정집을 만들어서 "뒷문은 원래 출입카드 전용이고, 로비에서 신분증 검사를 하는 이유는 이것"이라고 적어둔 겁니다. 새 경비원(새 팀원)이 와도 규정집만 읽으면 됩니다.
