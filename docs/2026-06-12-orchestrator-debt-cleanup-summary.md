## 1. 환경설정 파일(.env)을 매번 읽던 문제 → 한 번만 읽고 캐시

**무엇을:** `.env` / `docs/api_key.env` 파일을 파싱하는 `_load_dotenv()` 함수에 `@lru_cache`를 붙였습니다.

> 💡 **쉽게 말하면:** 매번 책장에서 같은 책을 꺼내 읽던 걸, 한 번 읽고 머릿속에 외워두는 걸로 바꿨습니다. 단, "지금 누가 말로 알려주는 값(OS 환경변수)"은 항상 최신으로 듣습니다.

**커밋:** `63b546a1` · **파일:** `orchestrator/app/api/routers/generation_jobs.py`

**어떻게:** 모드→엔진 대응표를 파일 상단에 데이터로 선언하고, 라우터는 표를 조회만 합니다. 기존 13개 문자열과 엔진 이름은 한 글자도 바뀌지 않았습니다(테스트로 고정).

## 3. LLM이 이상한 형태로 답하면 원인 모를 에러 → 명확한 에러 메시지

**커밋:** `f2276e40` · **파일:** `orchestrator/app/llm/node_runner.py`

**무엇을:** `validate_output()`에서 LLM 출력이 딕셔너리(Mapping)가 아닐 때(예: 리스트로 답변) 정체불명의 `TypeError` 대신 `"LLM output for CopySpec must be a mapping, got list"` 같은 명확한 `ValueError`를 던지도록 했습니다.

**왜:** 기존에는 `output_schema(**output)` 언팩이 터지면서 알아보기 힘든 에러가 fallback 로그에 남았습니다. "왜 fallback이 발동했지?"를 디버깅할 때 원인을 알 수 없었어요.

**어떻게:** 언팩 직전에 타입을 검사해서 명시적으로 에러를 던집니다. **중요한 점:** 에러가 나면 fallback으로 넘어가는 기존 안전망은 그대로입니다. 바뀐 건 로그에 남는 이유 문구뿐입니다.

> 💡 **쉽게 말하면:** 기계가 고장 났을 때 그냥 "에러!"라고 빨간불만 켜던 걸, "3번 부품이 규격에 안 맞습니다"라고 알려주게 한 겁니다. 고장 시 비상정지(fallback)하는 건 똑같습니다.

**커밋:** `ac91b7e1` · **파일:** `orchestrator/app/llm/nodes/copy_candidates.py`

**무엇을:** 전화번호/가격 정규식 검사 함수 두 곳에서 함수 내부에 있던 `import re`를 모듈 최상단으로 올렸습니다.

**왜:** 함수 안 import는 순환참조를 피할 때나 쓰는 패턴인데, `re`는 표준 라이브러리라 그럴 이유가 없습니다. 읽는 사람이 "왜 여기서 import하지? 뭔가 사정이 있나?"라고 불필요하게 고민하게 만듭니다.

> 💡 **쉽게 말하면:** 요리할 때마다 서랍에서 칼을 꺼냈다 넣었다 하던 걸, 처음부터 도마 옆에 놔두는 걸로 바꿨습니다.

## 5. 있지도 않은 경우를 대비하던 hasattr 검사 → 삭제

**커밋:** `280fcea1` · **파일:** `orchestrator/app/graph/state.py`

**무엇을:** `create_initial_marketing_state()` 안의 `request.source_asset_id if hasattr(request, "source_asset_id") else None` 패턴 4곳을 그냥 `request.source_asset_id`로 바꿨습니다.

**왜:** `source_asset_id`, `reference_asset_id`는 `InitialMarketingRequest` 스키마에 **이미 선언된 필드**입니다. Pydantic 모델은 선언된 필드를 항상 가지므로 `hasattr`은 절대 False가 되지 않는 죽은 코드였고, "스키마가 확정 안 된 채로 짠 코드"라는 인상을 줍니다.

**어떻게:** 삭제 전에 asset_id가 state로 잘 전달되는지 고정하는 테스트를 먼저 추가하고, 그 테스트가 전후 모두 통과하는 걸 확인했습니다.

> 💡 **쉽게 말하면:** "지갑이 있으면 지갑에서 카드를 꺼내라"라고 매번 확인하던 건데, 그 지갑은 항상 갖고 다니는 게 보장돼 있어서 확인 절차를 없앤 겁니다.

## 6. 같은 이름의 함수가 두 곳에 존재 → 이름으로 구분

**커밋:** `3069518a` · **파일:** `orchestrator/app/llm/node_runner.py`, 테스트 1개

**무엇을:** `append_model_selection` / `append_llm_call_result`가 `state.py`와 `node_runner.py` 양쪽에 같은 이름으로 정의돼 있었는데, node_runner 쪽을 `append_*_safe`로 이름을 바꿨습니다.

**왜:** 이름은 같은데 동작이 미묘하게 다릅니다 — node_runner 버전은 프롬프트 등 민감 정보를 지우는 sanitize 처리를 하고, state 버전은 안 합니다. 어느 걸 import했는지에 따라 동작이 달라지는 함정이었어요.

**어떻게:** **합치지 않고 이름만 바꿨습니다.** 두 함수의 다른 동작은 의도된 것이라, 합치면 동작이 바뀝니다. `_safe` 접미사로 "이건 sanitize하는 버전"임이 이름에서 드러나게 했습니다.

> 💡 **쉽게 말하면:** 회사에 김철수 대리가 두 명 있어서 메일이 자꾸 엉뚱한 사람에게 가던 상황입니다. 한 명을 "김철수(보안팀)"로 표기하게 한 거예요. 두 사람을 한 명으로 합친 게 아닙니다.

## 7. "A가 바뀌면 B,C,D 다시 계산" 규칙이 if문 7덩어리 → 규칙 테이블

**커밋:** `17af171c` · **파일:** `orchestrator/app/graph/state.py`

**무엇을:** 사용자가 브리프를 수정했을 때 어떤 산출물(카피, 레이아웃, 프롬프트 등)을 다시 만들어야 하는지 계산하는 `calculate_dirty_fields()`의 중첩 if 체인을 `DIRTY_PROPAGATION_RULES`라는 선언형 규칙 테이블로 바꿨습니다.

```python
# (이게 바뀌면, → 이것들을 다시 만들어라)
(frozenset({"ad_format"}), frozenset({"ad_format_spec", "layout_spec"})),
```

**왜:** 이 규칙은 비용 절감의 핵심입니다(바뀐 것만 재생성 = LLM 호출 절약). 그런데 if문 속에 숨어 있으면 규칙을 추가/수정할 때마다 로직 전체를 다시 읽어야 하고, 실수가 테스트 없이는 안 보입니다.

**어떻게:** 리팩터링 **전에** 현재 if문의 출력값을 그대로 고정하는 특성화(characterization) 테스트 10개를 먼저 작성해 통과시킨 뒤, 테이블로 교체하고 같은 테스트가 그대로 통과하는 걸 확인했습니다. 즉 "전후 동작 동일"이 테스트로 증명돼 있습니다.

> 💡 **쉽게 말하면:** "밀가루가 바뀌면 빵이랑 면을 다시 만들어야 한다" 같은 규칙들이 요리사 머릿속(if문)에만 있던 걸, 주방 벽에 규칙표로 붙여놓은 겁니다. 규칙표를 바꾸기 전후로 같은 주문에 같은 요리가 나오는지 10가지 케이스로 검사까지 해뒀습니다.
