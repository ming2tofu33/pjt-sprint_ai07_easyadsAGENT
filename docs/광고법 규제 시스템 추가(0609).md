# 광고법 규제 시스템 추가(0609)

# 한국 광고 규제 Compliance Gate 도입 설계안

결론부터 말하면, 지금 실험한 제약 프롬프트는 방향은 맞지만 **프롬프트만으로는 부족하다.** 실제 출력에서도 `디톡스`, `4주 만에`, `4주 안에`, `변화` 같은 표현이 남아 있었기 때문에, 이건 “LLM에게 조심하라고 말하는 문제”가 아니라 **카피 생성 전·후에 deterministic rule gate를 두는 문제**로 봐야 한다.

현재 LangGraph 구조에서는 `tone_binding`이 직접 카피를 검수하는 노드라기보다는, 카피 생성 모드로 라우팅하기 전의 톤·방향 설정 노드에 가깝다. 실제 카피 생성/검증 흐름은 `tone_binding → copy_candidate_generation / auto_pilot_copywriting / custom_copy_validation → copy_spec_parser` 쪽이다. 첨부된 graph 정의에서도 `tone_binding` 이후 `copy_candidate_generation`, `auto_pilot_copywriting`, `custom_copy_validation`, `no_copy_bypass`로 분기하고, 이후 공통으로 `copy_spec_parser`에 합류한다.

따라서 광고법 규제 검증은 `tone_binding`에 몰아넣기보다, **새로운 `copy_compliance_gate` 노드**를 만들어서 카피 생성/사용자 입력 직후, `copy_spec_parser` 이전에 넣는 구조가 가장 맞다.

## 1. 현재 LangGraph에서 어느 노드가 카피 검증 역할인가

현재 구조를 역할별로 보면 다음과 같다.

| 영역 | 현재 노드 | 역할 | 광고법 검증 적합도 |
| --- | --- | --- | --- |
| 입력 정보 부족 검증 | `validator` | 업종, 상품, 채널, 목표 등 필요한 정보 확인 | “위험 요청 감지”에는 적합 |
| 톤/브랜드 방향 | `tone_binding` | 카피 톤과 브랜드 느낌 연결 | 규제 검증 주체로는 부적합 |
| 후보 카피 생성 | `copy_candidate_generation` | 여러 카피 후보 생성 | 프롬프트 제약 주입 필요 |
| 자동 카피 생성 | `auto_pilot_copywriting` | 자동으로 최종 카피 생성 | 프롬프트 제약 주입 필요 |
| 사용자 직접 카피 검증 | `custom_copy_validation` | 사용자가 직접 입력한 카피 검증 | 규제 검증과 결합 가능 |
| 카피 품질 후처리 | `copy_quality`, `copy_tone_policy` | 길이, CTA, 저품질 표현 보정 | 광고법 검증으로 확장 가능 |
| 최종 이미지 검수 | `readability_gate`, `final_validation`, OCR/VLM gate | 합성 후 가독성·OCR·품질 검수 | 최종 이미지 내 문구 검증에 적합 |

첨부 레포믹스 기준으로 `copy_candidate_generation_node()`는 `run_structured_node()`를 통해 LLM 또는 fallback으로 카피 후보를 만들고, 이후 `apply_candidate_quality_policy()`를 적용한다. 즉 이미 “생성 후 품질 정책 적용”이라는 훅이 존재한다. 여기에 광고법 compliance policy를 추가하기 좋다.

또 최근 구조에는 `copy_tone_policy.normalize_copy_for_business`, `build_copy_generation_metadata`, `metadata_contract_to_prompt_json` 같은 메타데이터 기반 생성 계약이 들어가 있다. 이 말은 compliance rule을 LLM prompt에 주입할 수 있는 구조도 이미 어느 정도 준비되어 있다는 뜻이다.

## 2. 추천 구조: Compliance를 4단계로 나누기

광고법 규제 검증은 한 노드에서 끝내면 안 된다. 다음 4단계가 필요하다.

```
1. 입력 요청 단계: 위험한 사용자 요구 감지
2. 카피 생성 단계: LLM prompt에 업종별 금지 규칙 주입
3. 카피 후처리 단계: 생성된 카피를 rule-based compliance gate로 검증·수정
4. 최종 이미지 단계: OCR/VLM으로 이미지에 실제 들어간 문구 재검증
```

### 권장 Graph 위치

현재 구조를 기준으로 하면 다음이 가장 자연스럽다.

```
validator
→ format_planner
→ tone_binding
→ copy_mode_router
   ├─ copy_candidate_generation
   │  → copy_candidate_compliance_gate
   │  → copy_candidate_selection_interrupt
   │  → state_update_selected_copy
   │  → selected_copy_compliance_gate
   │
   ├─ auto_pilot_copywriting
   │  → copy_compliance_gate
   │
   ├─ custom_copy_input
   │  → custom_copy_validation
   │  → copy_compliance_gate
   │
   └─ no_copy_bypass
      → copy_spec_parser

공통:
copy_compliance_gate
→ copy_spec_parser
→ text_style_binder
→ text_layout_planner
→ image_prompt_planner
→ prompt_renderer
→ t2i_request_builder
→ t2i_generation
→ background_validation / OCR
→ text_renderer
→ readability_gate
→ final_validation
→ result
```

후보 카피 모드에서는 두 번 검사하는 게 좋다.

첫 번째는 후보 리스트를 사용자에게 보여주기 전 필터링이다. 위험 후보를 그대로 UI에 노출하면 사용자가 선택할 수 있기 때문이다.

두 번째는 사용자가 선택한 최종 카피를 `copy_spec_parser`로 넘기기 전 검사다.

## 5. Prompt에만 넣지 말고 Rule Engine을 둬야 하는 이유

팀원이 한 실험에서 제약 프롬프트 적용 후에도 `디톡스`, `4주 만에`, `4주 안에`, `목표를 현실로` 같은 표현이 남았다. 이건 LLM이 직접적인 금칙어 일부는 줄였지만, **암시 표현과 업종별 규제 리스크까지 안정적으로 통제하지 못했다**는 뜻이다.

따라서 구조는 이렇게 해야 한다.

```
LLM prompt 제약:
위험 표현을 덜 만들게 하는 1차 예방

Rule engine:
실제로 생성된 문구를 확정적으로 검사하는 2차 방어

Rewrite policy:
위험 문구를 안전 문구로 치환하는 3차 보정

Final OCR/VLM:
이미지에 실제 들어간 텍스트를 다시 확인하는 4차 검수
```

## 6. RAG가 필요한가, 내부 문서가 나은가

초기 버전에서는 **RAG보다 내부 규칙 문서/YAML이 낫다.**

이유는 명확하다.

1. 광고 문구 검수는 latency가 짧아야 한다.
2. 법령 원문은 길고 조문 구조가 복잡해서 매번 RAG 검색하면 결과가 불안정하다.
3. 실제 필요한 것은 “법령 전체”가 아니라 “업종별 금지 표현 → 안전 대체 표현 → 근거 조문” 매핑이다.
4. 사용자가 i 버튼을 눌렀을 때 보여줄 설명도 법령 원문 전체가 아니라 사람이 읽을 수 있는 summary여야 한다.

따라서 v1은 다음 구조가 좋다.

```
내부 curated rule pack
→ deterministic matcher
→ optional LLM rewrite
→ FE citation display
```

RAG는 v2 이후에 붙이는 게 적절하다.

```
v1:
YAML/JSON rule pack

v2:
법령/가이드라인 문서 chunking + 검색

v3:
RAG 검색 결과를 rule pack update 후보로 사용

v4:
관리자 화면에서 rule version 관리
```

| P1 | 전자상거래법/소비자보호 관련 고시 | 가격, 할인, 이벤트, 기간, 환불 조건 등 생성 방지 | 가짜 할인율, 임의 기간, 허위 재고 |
| P1 | 상표법/저작권/퍼블리시티 관련 내부 정책 | 유명인, 캐릭터, 대기업명, 경쟁사 비교 방지 | “스타벅스 느낌”, “아이유처럼”, “디즈니풍” |

일반 광고 공통 규제는 표시광고법을 중심으로 보면 된다. 표시광고법 제3조는 소비자를 속이거나 오인시킬 우려가 있는 부당한 표시·광고 행위를 금지하고, 공정위 자료도 부당 표시·광고를 거짓·과장, 기만, 부당 비교, 비방 유형으로 구분한다. ([법률정보사이트](https://www.law.go.kr/lsInfoP.do?lsiSeq=103831&utm_source=chatgpt.com))

식품/카페/음료 쪽은 식품표시광고법이 핵심이다. 식품안전나라 설명 기준으로 식품 등에 대해 질병 예방·치료 효능이 있는 것으로 인식될 우려가 있는 표시·광고, 의약품으로 인식될 우려가 있는 표시·광고, 건강기능식품이 아닌 것을 건강기능식품으로 인식하게 하는 광고 등이 부당 표시·광고 유형에 들어간다. ([식품안전나라](https://www.foodsafetykorea.go.kr/portal/board/board.do?ctgType=CTG_TYPE01&ctgryno=2255&menu_grp=MENU_NEW01&menu_no=4838&utm_source=chatgpt.com))

의료/피부과/시술 영역은 의료법 제56조가 핵심이다. 의료법은 의료인 등이 아닌 자의 의료광고를 제한하고, 치료 효과를 보장하거나 소비자를 현혹할 우려가 있는 광고를 금지하는 체계다. 관련 판례/해석에서도 환자의 치료경험담 등은 소비자로 하여금 치료 효과를 오인하게 할 수 있는 의료광고로 문제될 수 있다. ([법률정보사이트](https://www.law.go.kr/LSW/lsInfoP.do?ancYnChk=0&lsId=001788&utm_source=chatgpt.com))

화장품·뷰티 영역은 화장품법 제13조와 제14조가 중요하다. 화장품법 제13조는 의약품으로 잘못 인식할 우려가 있는 표시·광고, 기능성화장품 심사결과와 다른 광고, 소비자를 속이거나 잘못 인식하게 할 우려가 있는 광고를 금지한다. 또한 화장품법 제14조는 사실 관련 광고 내용에 대한 실증 의무를 둔다. ([법률정보사이트](https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=270323&utm_source=chatgpt.com))

특히 “탈모방지”, “탈모치료” 같은 표현은 화장품 표시·광고 관리 지침상 의약품 또는 기능성 오인 우려가 있는 금지표현으로 안내된 사례가 있다. 이 방식으로 “여드름 치료”, “피부질환 개선”, “100% 개선” 같은 표현도 rule pack에 넣는 게 타당하다. ([법률정보사이트](https://www.law.go.kr/LSW/cgmExpcInfoP.do?cgmExpcDatSeq=458514&mode=2&ofiClsCd=350123))

## 10. Backend 구현 흐름

### 10.1 입력 단계: validator에서 위험 요청 감지

사용자가 처음부터 위험한 요구를 할 수 있다.

예:

```
붓기 제거, 체지방 감소, 피부 개선 효과가 있는 것처럼 써줘
```

이 경우 `validator`는 단순히 missing field만 물어보면 안 된다. 다음과 같은 state를 남겨야 한다.

```json
{
  "input_compliance_risk": {
    "status": "risk_detected",
    "riskDomains": ["food", "medical_claim"],
    "findings": [
      {
        "matchedText": "붓기 제거",
        "severity": "block",
        "reason": "식품 광고에서 신체 개선·의학적 효능을 암시할 수 있습니다."
      }
    ],
    "safeDirection": "맛, 분위기, 재료, 경험 중심으로 카피를 생성합니다."
  }
}
```

중요한 점은 여기서 사용자를 막기만 하는 게 아니라, 생성 방향을 바꿔야 한다는 것이다.

```
사용자 요청:
붓기 제거 느낌으로 써줘

시스템 반영:
신체 효능 표현은 제외하고, 산뜻한 맛과 기분 좋은 경험 중심으로 생성
```

### 10.2 생성 단계: copy generation metadata에 규칙 주입

`build_copy_generation_metadata()` 또는 prompt builder에서 업종별 compliance summary를 넣는다.

```json
{
  "constraints": {
    "compliance": {
      "jurisdiction": "KR",
      "domains": ["food"],
      "blockedClaims": [
        "질병 예방·치료",
        "의학적 효능",
        "체중·체지방 감소",
        "피부 개선"
      ],
      "blockedTerms": [
        "디톡스",
        "붓기 제거",
        "체지방 감소",
        "다이어트 효과"
      ],
      "safeRewriteDirection": [
        "맛",
        "분위기",
        "재료",
        "감성",
        "경험"
      ]
    }
  }
}
```

단, 이건 보조 장치다. 최종 검수는 rule engine이 해야 한다.

### 10.3 생성 후 단계: `copy_compliance_gate`

입력:

```python
state["marketing_copy"]
state["copy_candidates"]
state["context"]["business_type"]
state["context"]["item_or_service"]
state["input_compliance_risk"]
```

출력:

```python
{
  "marketing_copy": rewritten_copy,
  "copy_candidates": rewritten_candidates,
  "copy_compliance_report": report,
  "copy_compliance_status": "rewritten",
  "status": "copy_compliance_checked"
}
```

정책:

```
block:
의료법/식품표시광고법상 명백한 위험 표현
→ 사용자에게 피드백 필요
→ 자동 대체 가능하면 rewrite
→ 대체 불가능하면 interrupt 또는 needs_review

rewrite:
위험하지만 안전 표현으로 바꿀 수 있음
→ rewrite 후 metadata에 원문/수정 사유 저장

warn:
객관적 근거가 있으면 가능할 수도 있음
→ 근거 자료가 없으면 약화 표현으로 수정

needs_evidence:
1위, 최고, 유일, 100% 같은 실증 필요 표현
→ evidence 없는 경우 rewrite
```

### 10.4 최종 이미지 단계: OCR/VLM 재검증

이미 OCR gate와 VLM quality gate를 만들었으므로, 최종 이미지에서는 다음을 확인하면 된다.

```
TextRenderer가 합성한 문구가 compliance-passed copy와 일치하는가
T2I background에 가짜 텍스트/워터마크/브랜드명이 들어갔는가
최종 이미지 OCR 결과에 금지 표현이 포함됐는가
```

OCR gate는 이미 `background_ocr_gate_node`, `final_ocr_gate_node` 형태로 분리되어 있고, public-safe OCR payload helper도 있다.

## 11. FE에서 구현해야 할 기능

Frontend는 단순히 “에러 표시”가 아니라, **규제 피드백을 사용자가 이해하고 수정 방향을 알 수 있게 보여주는 UI**가 필요하다.

### 11.1 카피 후보 카드에 Compliance Badge

카피 후보마다 상태 표시.

```
통과
수정됨
주의 필요
사용 불가
```

예:

```tsx
<ComplianceBadge status="rewritten" />
```

표시 문구:

```
일부 표현이 광고 규제 위험으로 안전하게 수정됐어요.
```

### 11.2 i 버튼 / Tooltip / Bottom Sheet

사용자가 i 버튼을 누르면 다음 정보 표시.

```
문제 표현:
100% 보장

이유:
효과를 보장하는 표현은 소비자를 오인시킬 수 있어요.

관련 기준:
표시·광고의 공정화에 관한 법률 제3조
소비자를 속이거나 소비자가 잘못 알 우려가 있는 부당한 표시·광고 금지

안전한 대체:
만족스러운 경험을 위한 맞춤 관리
```

### 11.3 위험 요청 입력 시 inline feedback

사용자가 입력창에 위험 표현을 넣었을 때 바로 표시.

```
"붓기 제거"는 식품 광고에서 신체 개선 효과로 오인될 수 있어요.
맛·향·분위기 중심 표현으로 바꿔 생성할게요.
```

### 11.4 Before/After 자동 경고

피부관리샵, 병원, 다이어트 관련 요청에서:

```
Before & After 느낌으로 써줘
```

가 들어오면 UI에서 바로 경고.

```
Before & After 방식은 업종에 따라 치료 효과를 보장하거나 소비자를 오인시킬 수 있어요.
대신 “상담”, “관리 경험”, “나에게 맞춘 케어” 중심으로 표현할게요.
```

### 11.5 수정 전/후 비교 UI

후보 카피가 자동 수정된 경우:

```
원문:
4주 만에 10kg 감량 보장

수정:
4주 동안 체계적으로 준비하는 바디프로필 코칭
```

이걸 보여주면 사용자가 “AI가 왜 약하게 썼는지” 이해한다.

### 11.6 최종 결과 화면의 Compliance Summary

최종 이미지 하단 또는 상세 정보에:

```
광고 규제 검토 완료
- 식품 효능 표현 제거
- 보장 표현 제거
- 임의 할인율 생성 없음
```

그리고 상세:

```
검토 기준 보기
```

## 13. RAG를 쓴다면 넣을 참조 문서

RAG를 꼭 쓴다면 원문 전체를 그대로 넣기보다 다음처럼 “공식 source + 정제된 internal summary”를 함께 넣는 구조가 좋다.

### RAG 문서 후보

```
1. 표시·광고의 공정화에 관한 법률
2. 표시·광고의 공정화에 관한 법률 시행령
3. 공정위 표시·광고 심사지침
4. 식품 등의 표시·광고에 관한 법률
5. 식품 등의 표시·광고에 관한 법률 시행령 별표 1
6. 건강기능식품 표시·광고 심의 기준
7. 의료법 제56조
8. 의료법 시행령 제23조
9. 의료광고 심의 관련 가이드라인
10. 화장품법 제13조, 제14조
11. 화장품법 시행규칙 표시·광고 준수사항
12. 화장품 표시·광고 관리 지침
13. 상표법/저작권/초상권 관련 내부 policy
```

RAG chunk는 다음 단위가 좋다.

```
law_name
article
paragraph
item
domain
prohibited_claim_type
plain_korean_summary
examples_unsafe
examples_safe
source_url
last_verified_at
```

단순히 법령 원문을 chunk로 넣으면 retrieval이 “제56조 전체” 같은 긴 문단을 가져와서 실제 카피 검수에는 비효율적이다.

# **자동규제 side effect → HITL 활용방안**

맞아. **자동 치환을 기본값으로 두면 사용자의 핵심 판매 포인트를 시스템이 임의로 제거하는 문제**가 생겨.

특히 다음 문구는 문구 자체만 보고 일괄 금지하기 어렵다.

```
디톡스
다이어트 효과
체지방 감소
피부 개선
4주 만에 변화
1위
최고
```

예를 들어 `4주 만에`가 “4주 만에 10kg 감량을 보장한다”는 뜻이면 위험하지만, “4주 과정의 바디프로필 준비반”이라는 사실을 설명하는 것은 다른 문제다. `다이어트 효과`도 일반 음료에는 부적절할 가능성이 높지만, 법적으로 인정된 기능성과 표시 범위를 갖춘 건강기능식품이라면 제품의 승인 범위와 실제 근거를 확인해야 한다. 식품 광고 법령도 부당 광고를 금지하는 동시에 실증자료 제출 구조를 두고 있으므로, **표현 탐지 → 즉시 삭제**가 아니라 **표현 탐지 → 근거·업종·상품 유형 확인**이 더 정확하다. ([법률정보사이트](https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=273799&utm_source=chatgpt.com))

따라서 `copy_compliance_gate`는 **자동 문구 교정 노드가 아니라 규제 위험 판정 및 HITL 분기 노드**로 설계하는 게 맞아.

# 수정된 기본 철학

기존 제안:

```
위험 표현 탐지
→ 시스템이 안전한 감성 문구로 자동 변경
```

수정안:

```
위험 표현 탐지
→ 위험 수준과 법적 근거 제시
→ 사실·근거자료 확인
→ 사용자 선택
   ├─ 원문 수정
   ├─ 시스템 제안 문구 사용
   ├─ 근거자료 제출 후 원문 유지
   ├─ 법적 위험을 인지하고 초안으로 계속
   └─ 생성 취소
```

중요한 원칙은 다음이야.

```
사용자 의도는 보존한다.
시스템은 몰래 문구를 바꾸지 않는다.
자동 수정은 사용자가 선택한 경우에만 적용한다.
위험 문구와 수정 문구를 모두 기록한다.
법적으로 명백하게 허용할 수 없는 경우에는 일반 override를 제공하지 않는다.
```

# 1. 모든 규제 표현을 같은 방식으로 처리하면 안 됨

Compliance 결과를 최소 네 단계로 분리해야 해.

## A. `pass`

문제가 없거나, 규칙에 걸리지 않은 상태.

```
“4주 동안 체계적으로 준비하는 바디프로필 클래스”
```

바로 다음 노드로 진행한다.

---

## B. `warn_and_confirm`

표현은 위험할 수 있지만 문맥·사실관계에 따라 사용할 여지가 있는 상태.

예:

```
4주 만에 변화
최고의 선택
전문가 추천
디톡스라는 제품명
```

사용자에게 다음처럼 묻는다.

```
“4주 만에 변화”는 프로그램 기간을 설명하는 문구인가요,
아니면 4주 내 신체 변화 결과를 보장하는 문구인가요?
```

선택:

```
- 프로그램 기간만 의미해요
- 신체 변화 효과를 강조하고 싶어요
- 문구를 수정할게요
```

---

## C. `evidence_required`

객관적 근거가 있다면 쓸 여지가 있지만, 현재 시스템에 근거가 없는 상태.

예:

```
판매량 1위
국내 최초
체지방 감소에 도움
임상시험으로 확인
고객 만족도 98%
```

사용자에게:

```
“판매량 1위” 표현은 비교 기준·조사 기간·조사 기관 등
객관적 근거가 필요할 수 있어요.

근거자료가 있나요?
```

선택:

```
- 근거자료 업로드
- 출처와 기간 직접 입력
- 표현을 완화
- 해당 문구 제외
```

근거가 없는데도 사용자가 계속 사용하겠다고 하면, 정상 승인 상태가 아니라:

```
status=manual_review_required
```

로 진행해야 해.

---

## D. `block_or_legal_review`

사용자 확인만으로 허용하기 어려운 고위험 표현.

예를 들어 의료광고에서는 치료경험담 등 치료 효과를 오인하게 할 우려가 있는 내용, 거짓 내용, 객관적 사실의 과장 등이 명시적으로 제한된다. 이런 경우 단순히 “위험을 감수하고 계속”이라는 버튼만 제공하면 제품이 사실상 위법 가능성이 높은 광고 생성을 지원하게 된다. ([법률정보사이트](https://www.law.go.kr/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=1000180381&utm_source=chatgpt.com))

예:

```
여드름 완치 보장
치료 효과 100% 보장
환자 치료 후기 기반 확실한 효과
허가되지 않은 치료 효능
```

선택:

```
- 문구 수정
- 근거·허가·심의 자료 제출
- 법률/광고 담당자 검토 요청
- 생성 취소
```

일반적인:

```
“그래도 그냥 진행”
```

은 제공하지 않는 편이 맞아.

# 2. “사용자 override”를 어떻게 설계할 것인가

사용자가 모든 경고를 무시하고 바로 진행할 수 있게 하면 Compliance Gate가 유명무실해진다.

따라서 override에도 등급이 필요해.

| 결정 | 원문 유지 가능 | 조건 |
| --- | --- | --- |
| `pass` | 가능 | 바로 진행 |
| `warn_and_confirm` | 가능 | 위험 고지 확인 |
| `evidence_required` | 조건부 | 근거자료 또는 출처 입력 |
| `manual_review_required` | 초안만 가능 | 최종 광고 사용·배포 상태로 승인하지 않음 |
| `blocked` | 불가 | 문구 수정 또는 전문 검토 필요 |

핵심은 `사용자가 선택했다`와 `법적 검증을 통과했다`를 분리하는 거야.

```
user_override=true
≠
compliance_passed=true
```

예:

```json
{
  "complianceStatus": "manual_review_required",
  "userDecision": "keep_original",
  "userAcknowledgedRisk": true,
  "publicationReady": false
}
```

이 광고는 이미지 초안까지 만들 수는 있지만:

```
광고 규제 검토 필요
게시 전 법률·광고 담당자의 확인이 필요합니다.
```

라는 상태로 남겨야 한다.

# 3. `copy_compliance_gate`의 역할 재정의

새 노드는 카피를 직접 바꾸지 않는다.

## 입력

```
사용자 원래 요청
선택된 카피 또는 자동 생성 카피
업종
상품 유형
프로모션 목적
사용자가 제공한 사실
첨부 근거자료
이전 Compliance 결정
```

## 출력

```python
{
    "status": "warn_and_confirm",
    "findings": [...],
    "original_copy": {...},
    "suggested_copy": {...},
    "evidence_requirements": [...],
    "allowed_actions": [
        "keep_original",
        "use_suggestion",
        "edit_manually",
        "submit_evidence",
        "cancel",
    ],
}
```

## 하지 말아야 할 것

```
원문을 자동으로 덮어쓰기
원문을 state에서 삭제
사용자 몰래 표현 완화
모든 효능 표현을 감성 문구로 변경
경고 상태를 pass로 위장
```

# 4. 권장 LangGraph 흐름

현재 구조에는 이미 `interrupt()`를 사용하는 카피 후보 선택과 사용자 직접 카피 입력 흐름이 있다. 후보 선택 노드는 `copy_candidate_selection_interrupt`, 직접 입력은 `custom_copy_input_interrupt_node`로 구현되어 있고, 체크포인터 기반 중단·재개 구조를 재사용할 수 있다.

따라서 다음 흐름이 자연스러워.

```
tone_binding
→ copy mode 분기
```

## 후보 추천 모드

```
copy_candidate_generation
→ candidate_compliance_scan
→ copy_candidate_selection_interrupt
→ state_update_selected_copy
→ copy_compliance_gate
→ compliance router
   ├─ pass → copy_spec_parser
   ├─ warn/evidence → copy_compliance_interrupt
   └─ block → copy_compliance_interrupt
```

후보 생성 직후 검사는 후보에 badge를 붙이는 용도야. 이때 후보를 자동 제거하지 말고 위험 정보를 함께 내려보낼 수 있다.

```json
{
  "id": "cand_002",
  "headline": "4주 만에 달라지는 나",
  "compliance": {
    "status": "warn_and_confirm",
    "riskLevel": "medium",
    "findingCount": 1
  }
}
```

다만 `blocked` 수준의 후보는 기본 선택 대상에서 비활성화하는 게 좋다.

# 6. 사용자 응답 처리 노드

Interrupt 뒤에는 별도의 resolution node가 필요해.

```
copy_compliance_resolution
```

## `use_suggestion`

```
suggested_copy를 marketing_copy로 적용
original_copy는 audit metadata에 보존
compliance_status=rewritten_by_user_choice
```

## `edit_manually`

```
custom copy 입력 interrupt로 이동
사용자가 수정한 카피를 다시 compliance gate에서 검사
```

## `submit_evidence`

```
evidence upload/entry 단계
→ evidence metadata 저장
→ compliance gate 재평가
```

## `keep_original_draft`

```
원문 유지
user_acknowledged_risk=true
publication_ready=false
compliance_status=manual_review_required
→ copy_spec_parser로 진행 가능
```

## `cancel`

```
Job status=cancelled 또는 blocked
```

# 8. Rule pack도 “금지어 사전”이 아니라 조건부 정책이어야 함

예를 들어 기존처럼:

```yaml
patterns:
  - 디톡스
severity: block
```

으로 만들면 너무 단순해.

다음처럼 구성해야 해.

```yaml
- rule_id: KR-FOOD-DETOX-001
  term: "디톡스"

  contexts:
    product_name:
      decision: warn_and_confirm
      message: "정식 상품명인지 확인이 필요합니다."

    general_food_effect_claim:
      decision: evidence_required
      message: "일반 식품이 신체의 독소를 배출하는 것으로 오인될 수 있습니다."

    approved_functional_claim:
      decision: manual_review_required
      message: "승인된 기능성 내용과 실제 표시 범위를 확인해야 합니다."

  evidence_fields:
    - product_category
    - official_product_name
    - approved_claim_text
    - approval_or_report_number
```

`4주 만에`도 동일해.

```yaml
- rule_id: KR-FITNESS-DURATION-001
  pattern: "4주 만에"

  contexts:
    program_duration:
      decision: pass

    guaranteed_body_change:
      decision: evidence_required

    guaranteed_weight_loss:
      decision: manual_review_required
```

즉 단순 문자열 매칭 후 LLM 또는 deterministic context classifier가:

```
제품명인가?
기간 설명인가?
결과 보장인가?
실제 승인된 기능성 문구인가?
```

를 판별해야 해.

# 10. FE 경험

사용자 입장에서 가장 답답한 경험은:

```
원래 강조하고 싶던 내용을 AI가 아무 설명 없이 삭제
```

하는 거야.

좋은 UX는 다음과 같다.

## 경고 배너

```
광고 규제 위험 표현이 발견됐어요.

“체지방 감소”는 제품 유형과 승인된 기능성 범위에 따라
사용 가능 여부가 달라질 수 있어요.
```

## 선택지

```
[근거자료가 있어요]
[안전한 문구 제안 보기]
[직접 수정]
[위험을 확인하고 초안으로 계속]
```

## 원문/제안 비교

```
원문
체지방 감소를 돕는 디톡스 딸기라떼

시스템 제안
상큼한 딸기와 부드러운 라떼가 어우러진 한 잔
```

다만 제안 문구 하나만 강요하지 않고 여러 수준을 보여주는 게 좋다.

```
보수적:
상큼한 딸기와 부드러운 라떼가 어우러진 한 잔

의도 보존형:
가벼운 일상을 위한 딸기라떼

근거 확인 필요:
체지방 감소에 도움을 줄 수 있는 딸기라떼
```

마지막 문구는 승인·근거 확인 전에는 선택 시 `manual_review_required`로 둔다.

# 13. 의료·식품 영역에서의 예외 처리

모든 항목에 `그래도 진행`을 허용하면 안 된다고 본 이유도 있어.

의료광고는 치료 경험담, 거짓 내용, 객관적 사실 과장 등 특정 내용이 법률상 금지 범주로 규정돼 있다. 일반적인 제품 claim보다 사용자 재량 범위가 좁다. ([법률정보사이트](https://www.law.go.kr/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=1000180381&utm_source=chatgpt.com))

식품 광고도 질병 예방·치료 효능이나 의약품으로 오인하게 할 우려가 있는 표시·광고 등에 별도의 제한이 있다. ([법률정보사이트](https://www.law.go.kr/lsInfoP.do?lsId=013094&lsiSeq=269957&utm_source=chatgpt.com))

따라서 업종별로 다음처럼 달라야 해.

```
일반 서비스 최상급 표현
→ 근거 요구 + HITL

일반 식품의 치료·예방 표현
→ 강한 경고 + 근거/상품 유형 확인 + manual review

비의료기관의 의료행위 광고
→ block

의료광고의 치료 보장·허위·과장
→ block 또는 전문 심의 필요

승인된 기능성 표시 가능성이 있는 상품
→ 공식 표시문구와 승인 범위 확인
```

# 내 최종 의견

사용자에게 광고 효과를 강조하라고 요청받은 서비스가 모든 표현을:

```
맛있어요
산뜻해요
기분 좋아요
```

로만 바꿔버리면 법적으로 보수적일 수는 있어도 **광고 생성 제품으로서는 경쟁력이 없다.**

따라서 가장 좋은 원칙은 다음이야.

```
자동 삭제하지 않는다.
자동 덮어쓰지 않는다.
위험을 정확히 설명한다.
근거가 있으면 제출할 수 있게 한다.
사용자에게 선택권을 준다.
다만 법적으로 명백히 고위험인 영역은 무제한 override하지 않는다.
```

즉 `copy_compliance_gate`의 역할은:

```
검열기
```

가 아니라:

```
규제 위험 분석기
+ 법적 근거 안내기
+ 사용자 의사결정 분기기
+ 근거자료 요구기
```

여야 한다.

현재 프로젝트는 이미 `interrupt()` 기반 카피 선택·직접 입력과 GenerationJob answer/resume 구조를 갖고 있으므로, 이 HITL 방식은 기존 LangGraph 철학과도 잘 맞는다.
